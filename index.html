Q&A SOC: Questions d’entretien + Scénarios

Méthodologie à réciter: Détection → Qualification → Corrélation → Analyse comportementale (UEBA) → Réponse → Reporting. Toujours qualifier via multi-logs avant action; documenter les faux positifs.

Questions d’entretien (réponses courtes)

  • L1 vs L2: L1 qualifie/faux positifs; L2 investigue/corrèle/répond.
  • Faux positif: alerte valide techniquement mais activité légitime.
  • Qualifier une alerte: logs + contexte + comportement + corrélation.
  • MITRE ATT&CK: mapper tactiques/techniques pour détection & réponses.
  • SIEM saturé: réduire faux positifs via corrélation, contexte, UEBA.
Question RH: « Comment êtes-vous opérationnel sans expérience SOC dédiée ? »

Réponse: Environnements managés SOC (logs réels, WAF, firewalls, SIEM). Qualification, corrélation multi-logs, faux positifs vs incidents, méthodologie claire.

Question technique L1/L2: « Que faites-vous en premier à réception d’une alerte SIEM ? »

Réponse: Qualification: source, contexte, corrélation multi-logs; jamais bloquer sans comprendre.

Question client: « Trop d’alertes SIEM, que proposez-vous ? »

Réponse: Corrélation, contexte métier, UEBA; objectif = pertinence des alertes, pas quantité.

Cas pratiques (corrélation/UEBA)

Brute Force + Corrélation (IP interne, compte technique)

IP interne + compte svc_backup → faux positif probable. Corréler avec logs de backup/cron. Verdict: alerte valide mais légitime; documenter.

Phishing + UEBA (O365 login pays inhabituel)

Corrélation temporelle mail → login inhabituel; vérif MFA; reset mot de passe + investigation.

PowerShell encodé (utilisateur IT, heure ouvrée)

Vérifier signature/script SCCM/Intune; pas de connexions externes → faux positif maîtrisé.

Scénarios réalistes (20+)

Chaque scénario inclut: Contexte, Démarche, Actions, Checklist, et la logique faux-positif/corrélation/UEBA.

1) Brute Force SSH (Linux)

Contexte: Échecs SSH multiples depuis IP externe. Logs: /var/log/auth.log ou /var/log/secure.

  • Rechercher Failed password for → IP, utilisateur.
  • Si >5–10 échecs rapides → alerte pertinente.
  • Origine: réputation TI, géo, ASN.
  • Action: blocage firewall/fail2ban; vérifier compte.
  • Investigation: connexions Accepted password, propagation sur autres hôtes.
  • Prévention: clés SSH, désactiver password login.

Checklist: collecter logs, identifier pattern, blocage si nécessaire, corrélation, ticket SOC.

2) Email Phishing
  • Collecte: expéditeur, headers, URL en sandbox; ne pas ouvrir sur poste réel.
  • Analyse SIEM/Proxy: voir si domaine/URL déjà observé.
  • Action: isoler poste si clic; quarantaine mail; informer utilisateur.
  • Suivi: ticket SOC, verdict (phishing/spam/faux positif).
3) WAF: SQL Injection
  • Identifier URL, payload, IP; bloqué ou passé ?
  • Investigation: autres tentatives sur autres serveurs; logs applicatifs.
  • Action: bloc IP, mise à jour règle WAF.
  • Reporting: impact, mesures; escalade si données touchées.
4) Endpoint Malware/Ransomware
  • Isolation immédiate.
  • EDR: nom, hash, comportements; autres postes ?
  • Investigation: exfiltration, vecteur (mail/USB/téléchargement).
  • Réponse: nettoyage ou restauration; bloc règles endpoints.
  • Reporting: ticket détaillé, alerte SOC manager.
5) Trafic SMB suspect (vers extérieur)
  • Logs firewall/IDS: src/dst/port/heure.
  • Politique: autorisé ? compte compromis ?
  • Action: bloc IP externe; investiguer poste source.
  • Corrélation: endpoint/internes; ticket SOC.
6) Investigation Splunk
  • Définir index/sourcetype/time range.
  • Rechercher patterns: "Failed password", modsec_debug.
  • Corrélation: IP/utilisateur/serveur.
  • Dashboards/queries avancées.
  • Documentation exhaustive dans ticket.
7) Compte AD compromis
  • Logs DC: 4720/4728/4729/4732.
  • Identifier initiateur (SubjectUserName).
  • Corréler avec change management.
  • Revert si non autorisé; notifier sécurité.
8) Exfiltration de données
  • DLP/proxy: type de données, poste source, utilisateur.
  • Bloc destination suspecte.
  • Analyser légitimité vs règles métier.
  • Ticket avec verdict/actions.
9) Force brute FTP
  • Logs FTP: IP, compte.
  • Bloc IP suspecte.
  • Corrélation avec règles métier (transferts autorisés ?).
  • Reporting + recommandations.
10) RCE via JSP (ModSecurity)
  • Logs WAF + applicatifs; payload & IP.
  • Bloc IP; corrélation patterns similaires.
  • Ticket détaillé.
11) Déni de service (DoS)
  • Firewall/IDS/WAF: sources, volume, durée.
  • Mitigation: rate limit, blocage IP.
  • Vérifier impact; rapport détaillé.
12) Accès privilégié hors horaire
  • Logs: serveur, AD, VPN.
  • Confirmer via ticket change.
  • Doute → alerter sécurité; ticket.
13) Injection via API (JWT)
  • Vérifier headers/JWT; IP, endpoint.
  • Pattern répété/automatisé ?
  • Bloc IP/jeton; documentation.
14) Faux positif brute force SSH (interne)
  • Logs SSH; utilisateur concerné.
  • Corréler: déploiements, scripts automation.
  • IP interne légitime (Ansible/Bastion/Supervision) → faux positif.
  • Checklist: IP interne, compte technique, horaire, activité récurrente, documenter SIEM.
15) Corrélation Phishing → EDR
  • Vérifier clic utilisateur; corréler mail/proxy/EDR.
  • Process suspects, connexions sortantes.
  • Décision: clic + exécution → incident; pas de clic → faux positif EDR possible.
16) UEBA: connexion AD anormale
  • Comparer habitudes: heures, pays, serveurs.
  • Vérifier VPN/astreinte.
  • Corréler: logs VPN/AD/serveur.
  • Anomalie confirmée → reset PW + investigation.
17) PowerShell encodé (faux positif possible)
  • Identifier utilisateur; script Base64; téléchargement externe ?
  • Corréler: tâche planifiée, SCCM/Intune.
  • Script IT → faux positif; C2 → incident critique.
18) SMB interne vs mouvement latéral
  • Heure, type de fichiers.
  • Backup/synchro ?
  • Corréler: création comptes, tentatives admin.
  • Indice attaque: SMB + création comptes → latéralisation.
19) SQLi faux positif WAF
  • Requête avec ' OR 1=1; paramètre utilisateur ? test interne ?
  • Préprod → souvent faux positif.
  • Faux positif → exception WAF documentée; attaque → bloc IP + alerte.
20) Exfiltration lente (Low & Slow)
  • Petit volume sortant chaque nuit.
  • Corrélation: proxy/DNS/firewall; domaines récents.
  • Conclusion: APT-like, incident avancé.
21) DNS tunneling
  • FQDN très longs, fréquence élevée, domaine inconnu.
  • Action: bloc domaine, investiguer poste, corréler EDR.
22) Ransomware (signaux précoces)
  • Désactivation AV, suppression shadow copies, scan réseau.
  • Action: isolation réseau, bloc comptes, escalade critique.

Template Reporting SOC

Incident: type, date, périmètre
  Analyse: sources/logs, corrélations, UEBA
  Impact: Faible / Moyen / Critique
  Actions: blocage, isolation, nettoyage
  Verdict: Incident confirmé / Faux positif
  Recommandations: prévention, détection, durcissement

Phrase clé entretien: « Je commence toujours par qualifier l’alerte via la corrélation multi-logs avant toute action ».

EDR: Investigation pratique

Checklist investigation

  • Contexte: utilisateur, machine, sensibilité, exposition réseau.
  • Processus: arbre, parents, horodatage, modules, signature/code-sign.
  • Fichiers: hash, réputation VT, persistance (RunKeys, services, tâches).
  • Réseau: destinations, ports, fréquence, JA3/SNI, proxy logs.
  • Mémoire: handles LSASS, injections, ETW patching.
  • EDR: politiques, tamper, exclusions abusives.

Actions

  • Isoler l'hôte, bloquer hachage/domaines/IOC.
  • Collecte: triage bundle (proc, reg, services, network, autoruns).
  • Recherche latérale: events voisins, mêmes IOC, même user.
  • Remédiation: supprimer persistance, patch, réinitialiser secrets.
  • Améliorer détection: règle EDR, corrélations SIEM, playbook SOAR.

SOAR: Playbooks type

Modèle playbook

  1. Ingestion alerte → enrichissement (CMDB, Threat Intel, GeoIP).
  2. Vérifications automatiques (user risk, asset criticality, priorités).
  3. Décisions: faux positif, suspicion, confirmé.
  4. Actions: bloc IOC, disable user, isoler endpoint.
  5. Évidence & ticketing: attacher artefacts, notifier, SLA.

Bonnes pratiques

  • Idempotence, journalisation claire, timeouts et reprises.
  • Variables secrètes en vault, RBAC précis, audit.
  • Tests unitaires de playbooks, mocks d'API, sandbox.

Entretien: méthode STAR

Structure

  • Situation: le contexte, le système, l'alerte.
  • Tâche: ton rôle/responsabilité.
  • Action: ce que tu as fait, étapes concrètes.
  • Résultat: impact, métriques, leçons, durcissement.

Exemples rapides

Ajout admin inattendu (AD)

S: Alerte 4728, ajout à Domain Admins hors CAB.
T: Vérifier légitimité, contenir si abus.
A: Corrélation 4672/4720/4769, vérif ticket change, disable compte, rollback groupe, IOC hunt, règle SIEM + SOAR disable user auto.
R: MTTR 25 min, 4 hôtes affectés, ajout détection et revue hebdo des groupes.

Dump LSASS bloqué par EDR

S: EDR signale accès LSASS par procdump.exe.
T: Confirmer, contenir, collecter preuves.
A: Isolement hôte, collecte volatile, KQL/SPL latéralisation, reset secrets, bloc hash, règle EDR custom.
R: Aucun exfil constaté, renforcement GPO (CredentialGuard), playbook SOAR enrichi.

Fiches mémo rapides

  • Admin ajouté: 4720/4728/4672 + check change/ticket + désactivation si doute.
  • Spray: 4625 bursts IP unique, verrouillage et MFA, bloc réseau.
  • Service 7045: chemin utilisateur/Temp suspect → supprimer service, Quarantaine binaire.
  • Beaconing: périodicité régulière + SNI générique → bloquer domaine + isoler.
  • Linux SSH: PasswordAuth=no, Fail2ban, clés fortes, MFA.

Détection avancée : YARA rules

Structure : meta, strings, condition. Savoir créer, tester, activer, observer, désactiver (si faux positif).

Exemple — PowerShell suspect

rule Suspicious_PowerShell {
  meta:
    description = "Usage suspect de PowerShell"
    author = "Candidate"
  strings:
    $invoke = "Invoke-Expression" nocase
    $dlstr = "DownloadString" nocase
  condition:
    all of ($invoke, $dlstr)
}

Cible des loaders/scripting. À tester sur des échantillons contrôlés, activer en mode alerte.

Exemple — Indicateurs de fileless

rule PS_Fileless_Indicators {
  meta:
    description = "Arguments typiques de scripts fileless"
  strings:
    $nop = " -nop "
    $hidden = " -w hidden"
    $encoded = " -enc "
    $iex = /\|\s*iex/i
  condition:
    any of ($nop, $hidden, $encoded) and $iex
}

Détecte mix d’arguments (-nop, -w hidden, -enc) et exécution via iex.

Exemple — Macro Office → PowerShell

rule Office_Macro_PowerShell_Chain {
  meta:
    description = "Doc Office déclenchant PowerShell"
  strings:
    $ps = "powershell.exe" nocase
    $word = "winword.exe" nocase
    $excel = "excel.exe" nocase
  condition:
    1 of ($word, $excel) and $ps
}

À utiliser avec contexte process/parent fourni par l’EDR.

Exemple — URL externe dans script

rule PS_Download_From_URL {
  meta:
    description = "Téléchargement depuis URL externe"
  strings:
    $webclient = "Net.WebClient" nocase
    $download = "DownloadString" nocase
    $http = /http:\/\// nocase
    $https = /https:\/\// nocase
  condition:
    all of ($webclient, $download) and any of ($http, $https)
}

À corréler avec Threat Intel (domaine/IP) pour réduire faux positifs.

Scénarios d’incident (réponses modèles)

Scénario 1 — Suspicious PowerShell Download

Contexte: PC-SALES-03, utilisateur tbernard, powershell.exe parent winword.exe avec commande de téléchargement externe.

  1. Vérifier sévérité et type de détection (PowerShell anormal, téléchargement URL externe)
  2. Valider utilisateur/rôle/privileges (impact potentiel)
  3. Process tree: winword.exe → powershell.exe (macro malveillante probable)
  4. Timeline: événements avant (fichier Office reçu/email), pendant, après
  5. IOAs/IOCs: URL/script vus ailleurs (Threat Intel), règles YARA qui matchent
  6. Réponse: stop powershell.exe, quarantine artefacts, isoler la machine
  7. Artefacts: logs, enfants, exports (script, URL, réseau)
  8. Rapport & recommandations: filtrage macro, scan complet, YARA adaptées

Scénario 2 — Faux positif service système

Contexte: svchost.exe signalé par heuristique comportementale.

  1. Lire le détail d’alerte: quelles signatures/règles ont déclenché
  2. Comparer avec légitime: chemin (C:\\Windows\\System32\\svchost.exe), hash, arguments
  3. Autres indicateurs: réseau, enfants, registre
  4. Corréler via SIEM: événements Windows/Firewall
  5. Décision: documenter & allowlist si faux positif; sinon réponse (isolation/kill)
  6. Reporting systématique (ticket SOC) avec justification

Scénario 3 — Téléchargement MIME via email (macro Office)

Chaîne: OUTLOOK.EXE → excel.exe → PowerShell.

  1. Identifier vecteur: document Office reçu par email (expéditeur/objet/macro)
  2. Analyser le document en sandbox interne
  3. Tracer les commandes PowerShell et arguments
  4. IOAs: téléchargements externes, cmdlets suspects
  5. Réponse: bloquer URL, block hash du fichier, quarantine document
  6. Communication: alerte interne + sensibilisation macro; filtrage email/sandboxing
  7. Règles YARA spécifiques pour détecter ce comportement

Questions d’entretien & réponses

Q1 — EDR vs XDR

EDR: endpoints (collecte, détection, investigation, réponse). XDR: étend à réseau/cloud/email/siem avec corrélation multi-sources.

Q2 — Qu’est-ce qu’une règle YARA ?

Détection basée sur motifs (strings/patterns/conditions) pour fichiers/scripts/comportements. Réf: docs officielles YARA.

Q3 — Analyse d’une alerte HarfangLab

Contexte → Process tree → Timeline → Threat Intel → Réponse (kill/isolate/quarantine).

Q4 — Gestion d’un faux positif

Vérifier exécutable (chemin/signature/hash), corréler SIEM, décider (isoler/allowlist), documenter.
